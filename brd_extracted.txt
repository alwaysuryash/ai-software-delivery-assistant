2. Executive Summary
The AI Software Delivery Assistant is an AI-native enterprise application designed to reduce the manual effort required to
monitor software projects, prepare status reports, detect delivery risks, and coordinate follow -up actions. It will connect to
delivery systems such as Azure DevOps or Jira, source-code repositories, test-management tools, knowledge repositories,
and communication platforms.
The solution will use an orchestrator agent and specialized delivery agents for business analysis, development, quality
assurance, DevOps, and project management. It will retrieve project evidence, reason over current and historical data,
produce traceable recommendations, and require human approval before performing write actions.

3. Business Problem
Project delivery information is fragmented across work-management tools, source repositories, testing systems, deployment
pipelines, documents, emails, and chats.
Project managers and delivery leaders spend significant time collecting information, validating progress, identifying blocker s,
preparing reports, and following up with teams.
Existing dashboards show metrics but often do not explain why a project is at risk, what evidence supports the conclusion, or
what action should be taken next.
4. Product Vision
Provide every delivery manager with a secure AI co-pilot that understands the project context, continuously assembles
evidence, explains project health, and recommends practical next actions without replacing human accountability.

6. Scope
6.1 In Scope
• User authentication through Microsoft Entra ID or equivalent enterprise identity provider.
• Project selection and project-specific access control.
• Read integration with Azure DevOps or Jira, GitHub or Azure Repos, test-management data, CI/CD status, SharePoint or
Confluence, Teams or email summaries.
• AI-generated project-health summary, sprint summary, risk analysis, action list, stakeholder update, and evidence links.
• Multi-agent orchestration with PM, BA, Development, QA, and DevOps analysis.
• Human approval before creating or updating tickets, sending messages, or changing delivery systems.
• Audit trail covering prompts, tool calls, retrieved evidence, model outputs, approvals, and actions.
• Evaluation framework for groundedness, completeness, risk precision, and report usefulness.
6.2 Out of Scope for MVP
• Autonomous code merge or production deployment.
• Automatic employee performance scoring.
• Financial invoicing, payroll, or contract decisions.
• Unrestricted reading of all organizational email or chat content.
• Replacing formal project governance or customer approvals.
• Training a foundation model from scratch.

8. Primary Use Case: Daily Project Health
Trigger: The project manager selects a project and asks, “Give me today’s project health,” or a scheduled job prepares a draf t
report for review.
1. Authenticate the user and verify project access.
2. Load project configuration, reporting period, sprint dates, and source connectors.
3. Orchestrator decomposes the request into BA, Development, QA, DevOps, and PM analysis tasks.
4. Each agent retrieves only the minimum evidence required from authorized tools.
5. Agents return structured findings with evidence references, timestamps, confidence, and missing-data warnings.
6. Orchestrator reconciles contradictions, removes duplicates, and calculates overall health.
7. Evaluation layer checks grounding, data freshness, completeness, policy compliance, and unsupported claims.
8. Application displays the draft report with health, progress, risks, blockers, actions, decisions required, and evidence.
9. User edits or approves the report.
10. Any outbound action, such as updating a ticket or sending a stakeholder note, requires explicit user approval and is
logged.

11. Business Rules
Rule ID Rule
BR-01 No claim shall be presented as fact without retrieved evidence or an explicit “inference” label.
BR-02 No specialist agent may access a source unless the user and project configuration authorize it.
BR-03 No write action shall be executed without an approval record tied to the exact proposed payload.
BR-04 Health shall be “unknown” when minimum required data is unavailable; the system shall not guess.
BR-05 The latest source event timestamp shall be shown for all time-sensitive metrics.
BR-06 Conflicting evidence shall be displayed with an explanation; the system shall not silently choose one.
BR-07 Personal performance conclusions shall be excluded from MVP reports.
BR-08 The system shall minimize data retrieval and avoid sending secrets, source code, or sensitive data to models unless
explicitly approved and technically protected.
BR-09 Model output shall be treated as a draft until evaluation checks pass.
BR-10 A user correction shall not overwrite source-system evidence; it shall be stored as feedback or approved context.

14. Target Solution Architecture
Recommended logical components:
• Web UI: project selector, chat, health dashboard, evidence drawer, report editor, approval panel, feedback.
• Application API: authentication, authorization, project configuration, report management, approval workflow.
• Agent Orchestrator: task planning, agent invocation, state management, conflict resolution, and response assembly.
• Specialist Agents: BA, Development, QA, DevOps, PM.
• Tool Gateway / MCP Layer: standardized, permission-aware connectors to enterprise systems.
• Retrieval Layer: document ingestion, chunking, metadata filtering, hybrid search, and citations.
• Rules and Scoring Engine: deterministic metrics, thresholds, health calculation, and policy checks.
• Evaluation Layer: groundedness, completeness, contradiction, safety, freshness, and format validation.
• Data Stores: application database, vector index, short-term agent state, approved memory, audit log.
• Observability: logs, traces, metrics, token and cost tracking, model and tool performance.

16. Security, Governance, and Responsible AI
• Use least-privilege permissions for every connector.
• Separate read tools from write tools; disable write tools by default.
• Validate all tool arguments against strict schemas and approved resource scopes.
• Defend against prompt injection in retrieved documents by treating retrieved content as untrusted data, not instructions.
• Mask secrets, credentials, personal data, and restricted source code before model submission where required.
• Maintain immutable audit events for sensitive actions.
• Apply content filtering and organization-specific policies.
• Provide a kill switch per connector, project, model, or agent.
• Define data retention for prompts, retrieved text, outputs, embeddings, and logs.
• Conduct threat modeling before production rollout.

18. Step-by-Step Build Instructions
Phase 0 - Foundation and Decisions (1 week)
11. Confirm the MVP tool set: select one work-management tool, one source repository, one test source, and one document
source.
12. Define one pilot project and obtain read-only service credentials.
13. Agree health dimensions, thresholds, report template, and user roles.
14. Create threat model, data classification, and approval policy.
15. Create repositories, coding standards, environments, CI pipeline, and issue backlog.
Phase 1 - Application Skeleton (1-2 weeks)
16. Implement SSO and project-level RBAC.
17. Create project, connector, user-access, report, and audit database tables.
18. Build web shell with project selector and assistant workspace.
19. Implement correlation IDs, structured logging, error handling, and feature flags.
20. Add mock connectors and sample project data to unblock front-end and agent development.
Phase 2 - Read Connectors and Evidence (2 weeks)
21. Implement read-only connectors for backlog/work items, repository/PR/build data, test results/defects, and project
documents.
22. Normalize records into internal evidence schemas.
23. Add timestamp, source ID, deep link, project ID, sensitivity, and access metadata.
24. Implement timeouts, pagination, retries, rate-limit handling, and connector health checks.
25. Create contract tests with recorded non-sensitive fixtures.
Phase 3 - Deterministic Metrics and Health (1-2 weeks)
26. Implement sprint progress, overdue items, blocked work, PR age, build status, test pass rate, critical defects, and
deployment status.
27. Implement configurable thresholds and weighted health scoring.
28. Return unknown rather than green when required data is missing.
29. Write unit tests for every formula and threshold boundary.
Phase 4 - Single-Agent MVP (2 weeks)
30. Build one Delivery Analyst agent before implementing multiple agents.
31. Provide the agent only approved read tools and a strict output schema.
32. Require evidence IDs for every finding.
33. Add prompt-injection defenses, maximum tool-call limits, and execution timeout.
34. Generate the daily-health report and show citations in the UI.
Phase 5 - Multi-Agent Specialization (2-3 weeks)
35. Split the Delivery Analyst into BA, Development, QA, DevOps, and PM agents.
36. Implement an explicit orchestration graph with maximum steps and deterministic routing rules.
37. Run independent agent tasks in parallel where safe.
38. Implement contradiction detection and duplicate finding consolidation.
39. Do not expose private chain-of-thought; expose concise rationale and evidence only. --- PAGE 10 ---

Phase 6 - Evaluation and Quality Gates (2 weeks)
40. Create a gold dataset of realistic project snapshots and expected findings.
41. Implement groundedness, citation validity, freshness, completeness, schema, and policy evaluators.
42. Block report publication when critical evaluation checks fail.
43. Capture user feedback and compare against expected results.
44. Track quality by prompt version, model version, connector, and project.
Phase 7 - Human Approval and Write Actions (1-2 weeks)
45. Add message drafting and work-item update proposal generation.

48. Implement idempotency and rollback or compensation where the target system supports it.
49. Log the approving user, timestamp, result, and source evidence.
Phase 8 - Pilot and Production Hardening (2 weeks)
50. Run the solution with one project in shadow mode alongside the current manual process.
51. Compare AI reports to PM reports and classify misses and false positives.
52. Tune thresholds, prompts, tools, and report formatting.
53. Complete load, security, privacy, disaster recovery, and operational readiness testing.
54. Release to a limited user group and monitor adoption, quality, latency, and cost.

21. MVP Definition of Done
• SSO and project RBAC are operational and security-tested.
• At least four read-only source categories are integrated for one pilot project.
• Daily project-health report is generated with health, risks, actions, data gaps, and evidence.
• Every material statement is traceable to evidence or explicitly marked as inference.
• Deterministic scoring is implemented and unit-tested.
• Evaluation gates are executed and critical failures prevent publication.
• User feedback and audit trail are available.
• No write action occurs without explicit human approval.
• Operational dashboards show latency, failures, token usage, cost, evaluation scores, and connector health.
• Pilot acceptance criteria and responsible-AI review are approved.

Appendix C - Implementation Guardrails for the AI Developer
• Build the deterministic data and scoring foundation before adding agent autonomy.
• Prefer explicit workflows and typed schemas over open-ended agent loops.
• Never place raw credentials or secrets inside prompts.
• Do not store private chain-of-thought; store concise explanations, evidence, and decisions.
• Make every failure visible: partial source, stale data, timeout, denied access, evaluation failure.
• Version prompts, tools, models, thresholds, and evaluation datasets.
• Design every write action as a proposed, reviewable, idempotent transaction.
• Use representative but non-sensitive test data in development.
• Treat evaluation and observability as product features, not post-production tasks.
